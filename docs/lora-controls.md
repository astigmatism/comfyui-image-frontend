# Ordered LoRA controls

Published `lora_stack` inputs appear as a collapsible LoRAs section. Its header has a **Manage LoRAs** launch control beside the section expansion control, matching the focused prompt editor. The expanded section shows only enabled LoRAs in application order, with each image, name, and strength. The main sidebar provides an editable strength field with up/down buttons and an **×** button to disable each LoRA immediately. Arrows and keyboard Up/Down change strength by 0.5, or by the workflow’s published step if 0.5 is incompatible. Typed values retain the published precision and commit on Enter or blur; Escape restores the saved value. Zero disables a LoRA, preserving its previous strength and application order; a remembered strength may be negative, and so is a displayed one. A workflow may publish a range that reaches below zero, where a negative strength subtracts that LoRA from the model instead of adding it; **×**, **All off**, and every “enabled” count treat zero as the only unloaded value, in either direction. Sidebar shortcuts save settings without changing Subject name. The rerun dialog provides the same strength controls against its own draft, without changing the main sidebar. An empty section invites the user to open the manager. The image beside each entry is itself a control: clicking it, or pressing Enter or Space on it, copies that LoRA's published `trigger_word` to the clipboard, falling back to its published title where no trigger word is verified, and confirms which LoRA was copied in a toast. Copying reads the published catalog only — no selection, strength, application order, or Subject name changes — and stays available even when the row's other controls are disabled, including for a LoRA applied below zero.

The manager is a modal gallery, up to 1380 pixels wide, sized to 75% of its previous near-full-window width and height. Minimum dimensions keep controls usable in smaller windows; below 800 pixels it still fills the screen. A group heading follows the main gallery’s pattern: the group name, a hairline rule, a count, and, for administrators, icon controls for **Move up**, **Move down**, **Rename group**, and **Delete group**. LoRAs with a thumbnail form a responsive grid of square cards whose single-line caption carries the published name, an **Open Demo Reel** icon, and the actions menu. A LoRA without a thumbnail is an on/off switch rather than a portrait, so it takes one line in a compact list under that grid, holding only its name and the menu. The header's **Thumbnail size** slider scales every group's cards from 50% to 150%, reflowing the grid immediately; the compact list follows the slider but never narrows below a readable name. This browser remembers the size independently of selection Apply/Cancel. Click a thumbnail or a compact row (or press Enter/Space on it) to enable or disable the LoRA. Selected entries have a checkmark and accent border. Missing thumbnails remain selectable. Usage guidance and published trigger words are available from the card menu.

The **Application order** strip above the gallery shows enabled LoRAs independently of group/card sorting. Drag its handles with a mouse, touch, or pen, or use arrow keys on a focused handle. Reordering preserves each LoRA's strength and retains every disabled entry exactly once in the generation array. **All off** disables all entries without erasing remembered strengths. Enabling one restores its valid remembered strength, or the strength the workflow publishes for it in `preferred_strength`, or a positive value supported by the workflow. Strength is adjusted in the generation sidebar or the rerun dialog's editable LoRA summary; the gallery has no strength controls.

Selection and application order remain a draft until **Apply**. **Cancel**, Escape, and closing discard these edits. Nothing in the manager saves an image: a LoRA's picture is derived from its own Demo Reel, so it changes when somebody favorites there or when that slot produces its first image. A LoRA is drawn as a card while its picture exists and as a compact row while it does not, and the Demo Reel is one click away either way. A thumbnail belongs to the LoRA's shared identity, so every workflow that lists it shows the same image. Images are separate from generation payloads and never become ComfyUI selectors.

## Shared groups

The **Open Demo Reel** icon in a card's caption opens that LoRA's shared image
gallery; a LoRA without a thumbnail opens it from **Demo Reel** in its menu.
Administrators configure shared prompt slots and idle generation recipes through
the picker's **Demo Reel** subsection. Saved reel settings are independent of
selection Apply/Cancel. A LoRA an administrator has taken out of the reel has no
images and says so in place of waiting for them; it is otherwise an ordinary LoRA,
selectable and drawable in every generation. See
[LoRA Demo Reels](demo-reel.md).

Every LoRA belongs to one group per model-family library. Administrators create and rename groups and use a card's **Move to group** action to assign its LoRA. Each group heading has **Move up** and **Move down** controls, including Uncategorized. These changes are shared by all users and compatible workflows, save immediately, and are not undone by Cancel. Initially custom groups sort alphabetically, including empty groups, followed by **Uncategorized**. After reordering, the saved order survives renames and deletions; new groups appear immediately before Uncategorized. Cards remain alphabetical within each group. Gallery arrangement never determines generation order.

**Uncategorized** is permanent and cannot be renamed or deleted. Existing, newly installed, and newly discovered LoRAs start there. Deleting a custom group moves its members to Uncategorized without removing weights, thumbnails, or selections. Group names are trimmed, have 1–80 characters, and are unique without regard to case within a library. The application stores groups and single memberships by model family and shared LoRA identity, independently of ComfyUI publications. Revision checks reject concurrent edits; the manager reloads the latest grouping for review before an explicit retry.

Administrators also have **Add LoRA**, **New group**, title/trigger editing, deletion, and the **Library status** control beside the dialog's **✕** here. An account-menu **LoRA library** shortcut opens the same gallery in management mode with a model-family picker and Done, without generation selection or ordering controls. LoRA management is no longer part of Administration. Library operations preserve valid selection drafts while publications refresh, remove deleted entries, and add new entries disabled. An unsuccessful publication refresh blocks Apply until the current publication can be established by reopening the selector.

The LoRA list itself is a shared library maintained by administrators (see [Administrator LoRA management](lora-administration.md)). Switching workflows carries the LoRA picks with the rest of the control panel: order, enabled states, strengths, and remembered strengths follow each LoRA by its library ID, or by its shared identity when the IDs differ. A LoRA the new workflow does not publish is dropped, one only it publishes starts at its default strength, and when the two lists have nothing in common the new workflow keeps its own picks.

When Apply enables at least one LoRA, Prompt Generation → Subject name takes the published `trigger_word` of the first enabled LoRA **in application order** that publishes one. Strength never decides: a stronger LoRA further down the list waits its turn. A LoRA applied below zero never supplies it either — pulling a character the other way is not a claim about who is in the picture — even though that row's own tile still copies its trigger word. A LoRA with no published trigger word is treated as stylistic — it changes the picture rather than naming a subject — so it is passed over and its title is never used in its place; if nothing enabled publishes a trigger word, Apply leaves Subject name unchanged and the manager footer says so. Changing the prompt source keeps Subject name with the rest of the draft, and the qualifying LoRA outranks a subject typed by hand (see [Prompt generation](prompt-generation.md)). **All off** leaves Subject name unchanged. Copying an entry’s own tile still falls back to its title, because that is a deliberate choice of that one entry rather than a claim about the subject.

The manager shows published usage guidance in each card’s **Usage details** view. An optional public `description` on each catalog item supplies the text; omitted descriptions explicitly say that usage guidance was not published. Do not infer a trigger from a filename, or equate missing documentation with "no trigger required."

The Moody Krea2 Simple v31 conversion uses Spread, Claire, NexBlend08, and Tifa in that order, each initially zero, with range 0–2 and step 0.05. These are workflow-author constraints, not a claim about visual quality at high strengths or particular combinations. Krea 2 paints water droplets and a wet sheen on skin on its own; the community cure is the [Wetness Slider](https://civitai.com/models/2738333) LoRA loaded at −1.0, which is a LoRA subtracted from the model rather than one left out of it. Publishing that entry on this stack widens the range to −1–2: one control now takes the wetness off below zero and adds it above, while 0 still means the file is not loaded at all.

## Contract and execution

The public input contains `id`, `type: "lora_stack"`, normal display metadata, `items: [{id, label, description?, trigger_word?, preferred_strength?}]`, `minimum`, `maximum`, `step`, and `default: [{id, strength}]`. A request supplies one ordered array in `parameters.loras`. Every published ID must appear exactly once. Extra fields, missing/unknown/duplicate IDs, strings, booleans, nonfinite numbers, values outside the bounds, and values outside the decimal step are rejected. Omission uses the all-zero published default; explicit null is invalid.

`step` is positive and the range spans zero (`minimum <= 0 < maximum`), because zero has to stay inside the range: it is the published default and the only strength that leaves the model alone. A negative strength is a valid request, and the native loader receives it as a negative weight — the LoRA is applied, subtracted. Step alignment is measured from `minimum`; since every published default is zero, a publishable `minimum` is always a whole multiple of `step`, which is why the browser may measure the same grid from zero. `preferred_strength` is an optional per-item hint about which way one LoRA is meant to be pulled, so a stack that mixes character LoRAs with a subtracted wetness slider needs no second control. It must be a strength this stack accepts, it is allowed to be positive, and it changes nothing except the value a LoRA starts at when it is enabled; zero or an absent hint means no hint.

The trusted declaration binds only `CIFLoraStack.value`. The frozen graph retains `catalog_json`, a private array of `{id, label, filename, description?, trigger_word?, preferred_strength?}`. Descriptions are optional, nonblank plain text of at most 1000 characters; trigger words are optional, nonblank text of at most 1000 characters — a trigger is commonly a whole phrase describing the character (hair, eyes, styling), not one word. Publication checks its public projection (including all three optional fields) and defaults against that graph, and the browser receives neither filenames nor graph bindings. Existing publications without either field remain valid, and a catalog published under the earlier 120-character trigger cap stays valid: the cap is a maximum, so **Edit** republishes such a member with a longer phrase. The Save & Publish extension verifies the installed native loader inventory before publishing. Technical inventory describes `usage: "public_stack"`; it does not report every catalog member as active.

Usage text and verified trigger words belong to each workflow's catalog, not a frontend lookup keyed by a label. Library operations keep those fields identical across the workflows of one shared LoRA library, and a public ID always names the same private file there; library conflicts (one ID naming different files) block changes rather than attaching one model's instructions to another file. Workflow authors can update those fields in `catalog_json` and use **Save & Publish for Image Frontend** again. The separately enabled [administrator LoRA operation](lora-administration.md) can install or remove a catalog member through the ComfyUI companion; it requires a title and trigger word for every new upload.

LoRA loader tags such as `<lora:name:strength>` are not prompt triggers in this workflow: the model node applies the weights directly. Authors may separately recommend ordinary prompt words. For the installed Tifa LoRA, embedded training metadata contains `TifaLockhart`, matching the [archived author instructions](https://civitaiarchive.com/tungsten/models/E4eNd8HiSW/versions/KhBMbtMnBV) (original author LatentHeart; recommended strength 1.0). The repository's candidate catalog records that exact `trigger_word`. Original documentation for the exact Spread, Claire, and NexBlend08 files could not be verified during the September 14, 2026 update, so the candidate catalog does not claim trigger words for them. Those entries can be populated and republished after their exact triggers are verified.

`CIFLoraStack` uses ComfyUI's native `LoraLoaderModelOnly` sequentially. An all-zero configuration returns the exact incoming model without constructing a loader or loading weights. A nonzero request creates its own loader and passes the returned model to the next nonzero entry. There is no request-shared model or configuration cache in this node. Text-encoder connections remain unchanged.

The backend validates the selected execution runtime's companion node and complete catalog before acceptance and again before dispatch. A secondary runtime without those prerequisites is rejected, including for a zero stack. A stack whose range reaches below zero adds one prerequisite of its own: the companion has to declare widget bounds that let an author enter that floor, since ComfyUI clamps an unbounded FLOAT widget at zero. A runtime still running the companion that predates signed strengths is therefore refused, and the error names the companion package to update rather than the strength that looked fine on another runtime. Runtime inventory uses the adapter's latest health-probe snapshot; ComfyUI still performs its normal native validation at execution time.

Requested and effective arrays remain in existing generation JSON fields. Recall and details retain labels, order, and strengths. Historical records with no stack restore zero defaults. Checkpoint fan-out takes a deep snapshot before submission; later form edits affect future submissions. Derived thumbnails and group metadata have their own database migrations; the generation and public `lora_stack` payload contracts do not change.

## Package ownership

`comfyui_extension/comfyui-image-frontend-interface/` now owns the complete existing interface/publisher package alongside `cif_artifact_cleanup`. Install this directory as one ComfyUI custom-node package; no new Python dependencies are needed beyond ComfyUI's existing environment. Its browser extension registers **Save & Publish for Image Frontend**.

The standalone public validator in the companion package deliberately has no web-application imports. Its identical backend counterpart is checked by a parity test. Change both together. Existing publication/v1 inputs and legacy interface nodes continue to work; `lora_stack` is an additive supported type. Deploy the new frontend before publishing an interface containing it.

## Rollout

1. Preserve the current adjacent `.json`, `.api.json`, and `.interface.json` files with their exact bytes, plus the installed custom-node package and current frontend image tag. Keep workflow snapshots private; they can contain prompts and private model bindings.
2. Inspect the ComfyUI container's mounts and image build source. Install the entire companion package through the persistent custom-node mount or its image build source; do not rely on a write to an ephemeral container layer. Keep a backup of the previous package. Deploy the frontend image from the same feature commit, preserving its existing environment and data mounts.
3. Register the new node with a ComfyUI service restart when the runtime is idle. Verify `GET /object_info/CIFLoraStack` returns its definition. Check `GET /object_info/LoraLoaderModelOnly` contains all four original files. These checks do not generate images.
4. Run `python scripts/lora/prepare_workflow.py ROLLBACK_DIRECTORY OUTPUT_DIRECTORY`. It verifies publication hashes, checks node 822 and its model destinations, prepares the editable workflow and candidate API graph, and removes only the old loader's unused CLIP input. It refuses an unexpected graph. All other compiled nodes stay unchanged.
5. Inspect offline with `node scripts/lora/validate_candidate.mjs WORKFLOW_JSON API_JSON OBJECT_INFO_JSON`. The object-info snapshot must include the installed companion node. During pre-installation review it can instead contain the prospective node definition; that is a static check, not proof of live installation.
6. Open the prepared editable workflow in ComfyUI, save it at the existing `workflows/comfyui-image-frontend/Moody Krea2 Simple v31.json` path, and choose **Save & Publish for Image Frontend**. This invokes ComfyUI's official graph compiler, writes the frozen API graph, then publishes the manifest last. Do not queue the workflow during rollout.
7. Refresh Administration → Workflow diagnostics in the frontend. Verify source readiness, the four LoRA labels, zero defaults, range 0–2/step 0.05, and order. Verify primary, second-pass, upscale, prompt/CLIP, and output connections using the saved graph. Leave other runtimes unenabled until their companion and catalog are verified.

For rollback, restore the three-file bundle with the manifest last, refresh discovery, and then restore the previous node package/frontend image if needed. Keep user data and database files intact. Live image generation and visual combination testing remain a subsequent user-controlled step.

## Tests

Run the repository's Python tests excluding `live`, frontend tests/build, Ruff, mypy, and the Playwright LoRA spec. The checkpoint fan-out journey additionally exercises the real application UI against its local fake runtime. `backend/tests/unit/test_lora_stack.py` tests mocked loader order, zeros in both directions, signed bounds, isolation, publication drift/privacy, and runtime prerequisites; its subprocess runs the preserved legacy companion-node tests. The integration test verifies batch persistence and exact recall, including a strength below zero. None of these tests require a household ComfyUI runtime or load LoRA weights.

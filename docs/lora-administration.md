# Administrator LoRA management

## Ownership and storage

Ordinary generation already sends prompt submissions, per-job input images, targeted cancellations, and post-archive output cleanup to ComfyUI. Workflow discovery remains a read-only operation: the application reads ComfyUI's adjacent editable workflow, frozen API graph, and interface manifest, validates them, and snapshots accepted revisions. The browser never calls ComfyUI directly.

When enabled, Administration adds a separate, privileged command to the installed ComfyUI interface companion. The application authenticates the administrator, checks the expected publication revision and active work, and coordinates the operation. **ComfyUI writes its own model and publication files.** The authoritative mapping is still the private `CIFLoraStack.catalog_json` plus its published public items; the application does not maintain a second title/trigger/filename lookup. The application then refreshes normal discovery and accepts the resulting revision only if validation succeeds.

On the Samus production host, final weights belong beneath `/home/astigmatism/ai/models/loras/`, mounted as ComfyUI's LoRA model root. They do not belong in `ai/support/` or frontend `/data/uploads/`. The primary ComfyUI instance has a writable shared model mount; promptgen sees that same library read-only. Each instance owns its own workflow userdata tree. The frontend container needs no model or workflow bind mount.

## Shared LoRA library

LoRA administration manages a **library**, not one workflow. Every current image workflow on the authoritative (primary) image instance with exactly one supported `lora_stack` belongs to the library of its base-model family (from published `generation_source.base_model.family`; a missing family forms an "Other models" library), so LoRAs never cross model families. Each workflow's frozen `catalog_json` stays authoritative for its own executable graph; the library is the agreement between those catalogs. Members are **in sync** when they list the same items (ID, title, trigger, description, private file) in the same order.

- **Install, edit, and remove** require a synced library and change every member in one operation. A LoRA installed once appears in every member with the same public ID; removing it takes it out of every member and then deletes the weight once. The members never block their own shared LoRA's removal.
- **Sync** republishes only the out-of-sync members (for example a newly published workflow whose catalog is empty or older) with the library catalog: the ordered union of all members' LoRAs, led by the largest catalog, with titles and triggers from the newest publication. Sync never removes a LoRA.
- **Conflicts** — one public ID naming different files, or one file listed under different IDs — block every change until the workflows are republished consistently.
- Thumbnails belong to the LoRA's shared identity (a hash of its normalized private filename), so they are the same in every workflow. Each workflow still keeps its own per-user LoRA order, enabled state, and strengths.

Only one LoRA operation runs at a time. Library operations need the version 2 companion (`multi_source: true` in `/cif/lora-management/capabilities`).

## Operation sequence

1. Administration shows the library. Install supplies one `.safetensors` file, a display title, and a nonblank trigger word. The application generates the public item ID and captures the full expected revision of every member. Existing entries without a trigger word remain valid. Edit supplies a new title and trigger word for an existing ID; an empty trigger word clears it.
2. The browser sends the file as a raw request body through the application to the authenticated model-writer companion. Both hops stream bounded chunks; neither parses a multipart file into the frontend's 64 MiB `/tmp`. The companion stages the bytes outside the installed inventory, checks size/hash and the safetensors header, and activates a file under its configured LoRA root.
3. Each participating companion verifies its local previous publications and model inventory. One prepare request lists every target publication; the companion journals each target's exact prior and candidate bytes. A narrow patch updates only the known root-level `CIFLoraStack` editable widgets, frozen `catalog_json` and zero-strength `value`, matching public manifest declaration, and technical inventory. It records a new publication UUID per target, one shared time, and exact hashes. The optional browser-compiler hash is omitted because this operation does not run `graphToPrompt()`.
4. The application validates every target's candidate before commit and requires matching candidate bytes on replicas. ComfyUI commits targets in path order, writing each target's editable and API files and then its manifest as commit marker; a failure restores every target already written. The application refreshes every affected catalog and verifies each target's new revision and the complete file inventory before reporting success.
5. Remove performs the same publication update with the item omitted from every member, then physically deletes the weight **after** every replica is verified. The cross-publication check skips the operation's own targets before the change and runs again without exclusions before deletion. Removal is blocked if a current publication outside the operation, an active generation's frozen graph, an active native loader, or a native ComfyUI queue entry still needs it. Disabled rgthree slots and explanatory notes are not active loader references. The authoring scan checks root nodes and stored subgraph definitions conservatively, so even an unused definition can block deletion until its reference is cleared. An empty catalog leaves `CIFLoraStack` connected as a model passthrough. Direct submissions to ComfyUI must be kept quiescent for the entire removal; the companion checks its native queue before preparation and deletion, but those checks cannot prevent a new direct `/prompt` call between checks.

An edit uses the same conditional, replica-verified publication path as install and remove. It changes only the existing item's public title and optional trigger word in the editable catalog, frozen API graph, and public manifest. The ID, private filename, description, and weight bytes remain unchanged. No file is uploaded, staged, or deleted, and existing thumbnail and saved-item associations continue to use the same ID. A request that changes neither field is rejected.

All management routes are disabled until `CIF_LORA_MANAGEMENT_SECRET` is configured in the application and the participating ComfyUI processes. The application sends it only server-to-server; `Comfy-User` selects a userdata namespace and is not an authorization credential. The companion accepts no browser-authored host path, arbitrary graph, or general filesystem command. `CIF_LORA_UPLOAD_MAX_BYTES` is a separate model-upload limit; the existing image upload limit does not apply.

ComfyUI's browser **Save & Publish** command uses a separate, same-origin publisher lease route to avoid overlapping an administrator edit. The route requires `Sec-Fetch-Site: same-origin` when the browser sends Fetch Metadata and always requires an exact same-host `Origin`; browsers omit Fetch Metadata outside secure contexts, so a plain-HTTP LAN editor is accepted on the `Origin` check alone. An empty `Comfy-User` header (ComfyUI's single-user editor) means the `default` namespace. This route cannot install or delete a model or edit a publication; every `/cif/lora-management` route still requires the server-held secret. ComfyUI's existing authoring and userdata APIs remain within the ComfyUI access boundary, so the deployment must restrict direct access to that service to trusted clients. A client with direct HTTP access could spoof browser headers and interfere with a publisher lease.

Each ComfyUI process also needs `CIF_LORA_MANAGEMENT_ROOT` set to the **in-container** LoRA folder reported by ComfyUI, `CIF_LORA_MANAGEMENT_USER` set to its intended userdata namespace, and `CIF_LORA_MANAGEMENT_MODEL_WRITER=1` on exactly one instance. On Samus the in-container folder is `/opt/ComfyUI/models/loras`; the primary mounts its host model library read-write and promptgen mounts that same library read-only. Promptgen must use `CIF_LORA_MANAGEMENT_MODEL_WRITER=0` and must see staging files through its read-only mount. `CIF_LORA_MANAGEMENT_MAX_UPLOAD_BYTES` bounds the companion's incoming file and should be at least as large as the app's `CIF_LORA_UPLOAD_MAX_BYTES`. These variables belong in private runtime configuration, never in a browser asset or committed secret file. The application refuses management if any replica is unreachable, reports a different model-root identity, or disagrees on the published revision.

## Recovery and visible state

The application persists an operation ID, actor, every target's expected and candidate revision, phase, and result. The companion journals exact prior bundle bytes and staged/quarantined model state on persistent storage. An operation interrupted after one replica commits can resume or restore prior bundles while the weight remains available. Failed rollback is visible as repair required and blocks additional LoRA changes. A repeated request uses the operation ID to report the existing outcome rather than performing the mutation twice.

An install waiting for its file can be cancelled, which clears any staged copy under that operation ID. A subsequent operation request clears reservations that have waited more than an hour only after verified companion rollback; upload retries use the same operation ID and are accepted only for identical bytes while it remains in the staged phase.

Generation admission is gated for every target workflow while a removal is committing. Thumbnail pruning and saved-selection reconciliation follow a verified commit, so rollback does not silently erase shared images; republishing never hides a LoRA image. An open user LoRA manager draft becomes stale when the publication revision changes, including a metadata edit. Historical gallery records remain visible; deleting a weight prevents exact re-execution of an old graph that required it.

Samus mounts the primary's `custom_nodes` package read-write on primary and read-only on promptgen. Upgrade the shared companion package once and restart both processes to load it. Back up both publication triples and the companion package before upgrading. The existing app release runner updates only the app container; it does not upgrade or restart either ComfyUI instance. Wait for active ComfyUI and application generation queues to drain before either restart.

Rollout order for companion updates on Samus:

1. Verify both instances expose compatible `CIFLoraStack` nodes, model inventories, and byte-identical current publication triples. Preserve exact backups of the two triples and the installed companion package.
2. Install the reviewed companion package in the shared `custom_nodes` tree. Confirm the same private management secret is configured on the app and both ComfyUI processes, the LoRA root and userdata namespace on each, and the model-writer flag only on primary. Restart both ComfyUI processes, verify the management capability route from the app network, then deploy the application release through its normal runner.
3. For a new installation, perform one disposable `.safetensors` install with a title and trigger word, confirm the public item and weight in both ComfyUI inventories, then remove it and confirm publication parity, empty references, and file deletion. For a metadata-only release, edit a test entry's title or trigger, verify both publications and the unchanged model file, then restore the original metadata.
